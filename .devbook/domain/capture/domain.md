## Capture

```meta
type: aggregate
related: [.devbook/domain/inbox/domain.md#inbox-item, .devbook/domain/capture/domain.invariants.md#capture, .devbook/domain/inbox/domain.md#note, .devbook/arc42/06-runtime-view.md#mobile-note-sync]
aliases: [ItemCaptured]
```

A single acquired piece of raw content from one source, before it becomes an
Inbox Item. The aggregate guarantees that every capture is normalized into the
standard shape and keeps the
original source link and capture timestamp until delivery. Each capture is a
unique entry: the same content from two devices makes two captures. Edits follow
last-write-wins by timestamp.

A note the phone creates starts as a capture like any other, with an id the
phone mints. Unlike the others, it does not end at delivery. Its Inbox
Item has `Content Kind` `note` and keeps syncing with the phone, which may edit
it again. Those later edits are the Inbox Item's. See
[Note](../inbox/domain.md#note). The phone's Notes tab writes this kind of note.

The aggregate has no owned entities beyond its root. The `Source Metadata`
value object and the `Capture Source` enum carry what varies between captures. The
`Capture Attachment` value object describes the files a capture brings, and
`Event Facts` the dates and place an event page capture found.

### Source Metadata

```meta
type: value-object
aliases: [SourceMetadata]
```

Source-specific context attached to a capture, which is one of:

- a YouTube channel name;
- a clipped `source_url`;
- an email sender;
- an IDE file path, line and branch.

A capture from an agentic session tool such as the GitHub Copilot App uses the
same `ide` shape, with a `session_id` and the local worktree path in place
of an editor selection. Equality is by value. Its keys depend on
the `Capture Source`, and downstream domains read it only as provenance.

### Capture Attachment

```meta
type: value-object
related: [.devbook/arc42/adr/0014-attachments-travel-through-a-blob-store-beside-the-replica.md, .devbook/arc42/06-runtime-view.md#capture-attachments]
aliases: [AttachmentMetadata, attachment]
```

A file a capture brings with it, such as a slide photographed at a talk or a
handout PDF. It is described by:

- its `id`;
- its file `name`;
- its `contentType`;
- its `sizeBytes`;
- its `sha256`.

The capture holds this description only. The bytes live in the
attachment store under the same id, uploaded before the capture that names them
(local ADR 0014). The client mints the id, so an offline phone can name a
file before sending it. Equality is by value.

The store is a courier, not a home. Acknowledging the capture releases the files,
and a capture waiting longer than 30 days keeps its description but loses its
bytes. Once a desktop has taken the capture in, its Inbox Item owns a copy of
each file.

### Event Facts

```meta
type: value-object
related: [.devbook/domain/capture/features.md#event-page-monitor, .devbook/domain/events/domain.md#event-date, .devbook/domain/inbox/domain.md#event-facts]
```

What an [event page capture](features.md#event-page-monitor) read about the edition
beyond its text:

- an optional `start` and `end`, each a date, plus a time of day and its UTC offset
  when the source gave them;
- an optional `place`, as the page wrote it;
- the watched page it was read from, by its URL and its title.

A capture from any other source carries none. In code these ride the
`CaptureFacts` record beside the import manifest's facts, each field optional.
Equality is by value.

### Tag

```meta
type: value-object
```

A `#keyword` applied to a capture, either auto-generated by a source adapter
(e.g. `#capture/youtube`) or user-provided. Equality is by canonical `name`.

### Capture Source

```meta
type: enum
related: [.devbook/arc42/adr/0017-inbox-import-is-a-capture-source-with-a-markdown-manifest.md]
aliases: [CaptureSource, CaptureSourceKind, source]
```

Origin type of a capture. Values and meaning:

- `mobile` — quick entry from the mobile app by voice, text or share sheet, and
  a note created on the phone's Notes tab.
- `youtube` — a new video detected by the YouTube monitor.
- `website` — a change detected by the website monitor.
- `event_page` — a new edition read off a watched event page by the
  [event page monitor](features.md#event-page-monitor).
- `email` — a newsletter/summary ingested from an IMAP inbox.
- `web_clipper` — content clipped by the browser extension/bookmarklet.
- `ide` — content captured from an IDE-class host. It is a selection in an IDE
  extension adapter (VS Code, Visual Studio), or an in-session capture command
  from an agentic session tool such as the GitHub Copilot App.
- `manual` — drag-and-drop or pasted content imported by hand.
- `import` — an item read from an import manifest. A skill outside the product
  generates the manifest from another tool, Microsoft To Do first. Each item is
  delivered under `CaptureIds.For(import, "{tool}:{external_id}")`, so importing
  it again adds nothing (local ADR 0017). An item written without an
  `external_id` uses a fallback id, the hash of its title and `captured_at`.

## Source Adapter

```meta
type: domain-service
related: [.devbook/domain/inbox/domain.md#inbox-item, .devbook/arc42/06-runtime-view.md#mobile-capture-and-sync, .devbook/arc42/06-runtime-view.md#ide-context-aware-capture]
```

Coordinates acquisition for a given `Capture Source`. It covers:

- polling or event intake;
- retry with exponential backoff;
- offline-first buffering with background sync;
- normalization of raw content into a Capture.

Each source has a concrete adapter behind this service:

| Adapter | Source | Built |
| --- | --- | --- |
| Mobile app, through the sync service | `mobile` | yes |
| YouTube monitor | `youtube` | yes |
| Website monitor | `website` | yes |
| Event page monitor | `event_page` | planned |
| Import manifest | `import` | yes |
| Email ingestion | `email` | planned |
| Web clipper | `web_clipper` | planned |
| IDE extension adapter | `ide` | planned |
| GitHub Copilot App session adapter | `ide` | planned |
| Manual import | `manual` | planned |

The GitHub Copilot App adapter would run as a peer of the IDE extension adapters,
invoked by a session against its local worktree. It would use the same local-first
path as the Desktop App and never route credentials through the optional Cloud Service.

The behavior does not belong on the Capture aggregate. It spans external I/O,
scheduling, and transport, outside a single capture's consistency boundary.
A command or a scheduler invokes it as an application service.

## Delivery

```meta
type: domain-service
related: [.devbook/domain/inbox/domain.md#inbox-item]
```

Delivers a normalized Capture to the Inbox's
[incoming queue](../inbox/features.md#incoming-queue) as an Inbox Item, and emits
the `ItemCaptured` event. It is a service because delivery is a handoff across the
boundary between Capture and Inbox, not a state change inside the aggregate.
It runs after normalization completes.

## ItemCaptured

```meta
type: domain-event
related: [.devbook/domain/capture/domain.md#delivery]
```

Published by `Delivery` when a normalized Capture is handed off to the Inbox.
This is Capture's published language for intake into the Inbox's
[incoming queue](../inbox/features.md#incoming-queue).

### Payload

- `capture_id` - originating Capture identifier.
- `source` - `Capture Source` value.
- `title` - normalized title.
- `body_md` - normalized markdown body.
- `tags` - normalized tags.
- `source_url` - original link when present.
- `captured_at` - time the source was captured.
- `attachments` - `Capture Attachment` descriptions, when the capture brought
  files; each file is fetched from the attachment store by its id. Additive.
- `event` - the `Event Facts`, for an `event_page` capture: `start`, `end`,
  `place`, `target_url` and `target_title`. Each is optional. Additive.

### Consumers

- The Inbox's incoming queue, which creates the `Inbox Item` and owns its lifecycle
  from then on.

### Published language rules

- Capture owns the meaning of the fields above; consumers conform to the contract
  and do not depend on Capture's internal aggregate shape.
- Additive payload changes are allowed; breaking shape changes require coordinated
  versioning with Inbox.
