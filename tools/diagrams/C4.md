# The C4 model beside the architecture chapters

The arc42 chapters carry their diagrams as mermaid fences, and those fences stay
canonical — they are what the Markdown says, what a pull request diffs, and what
the desktop app draws by default. Two of them are already C4: a `C4Context` in
`.arc42/03-context-and-scope.md` and a `C4Container` in
`.arc42/05-building-block-view.md`.

This folder documents something else: a **C4 model of its own**, kept beside those
chapters as Structurizr DSL, authored in [c4hero][c4hero] and drawn by the app from
the DSL at read time. It is additive. Nothing replaces a fence, no fence is
generated, and both existing C4 fences keep their Archify artifacts.

The feature is behind the `c4-diagrams` flag on the settings screen, off by
default.

[c4hero]: https://github.com/c4hero/c4hero

## How this differs from Archify, and why the shape is different

`README.md` in this folder describes the Archify arrangement. The two look similar
from a distance and are not the same kind of thing, which is worth stating once
because almost every design difference follows from it.

| | Archify | C4 |
| --- | --- | --- |
| what is authored | a specification *re-authoring one fence* | a whole workspace that is in no chapter |
| what is committed | the specification **and** a rendered `.html` artifact | the `.dsl`, and an authored reference map |
| how it reaches a diagram | matched to a fence by SHA-256 of the fence | not attached to a fence at all |
| what draws it | Archify's own viewer, embedded | this product's own renderer, from the DSL on read |
| what can go stale | the artifact, silently — hence the hash | nothing; there is no second copy |

Because an Archify artifact is a re-authoring of a fence with nothing in it
pointing back, it *needs* the hash and it needs the `_archify/index.json` the hash is
filed in — a generated file, holding a mapping nobody wrote. A C4 workspace has
neither problem: it is derived from nothing, so there is nothing for it to drift from,
and **nothing beside it is generated.** The `references.json` here looks like that
index and is its opposite: authored, reviewed in the diff, and the one place the link
to the chapters is stated.

## Where things live

```
.arc42/_c4/
    backlog.dsl              the workspace — authored, canonical
    references.json          which chapter each view documents — authored
    backlog.c4hero.json      c4hero's layout sidecar, written by c4hero
```

The sidecar holds node positions and viewport state. It is **not authored by hand
and not read by the app**: its schema is c4hero's, and hand-writing one would be
inventing a format. c4hero creates it on first save; the app ignores it and lays
views out through mermaid instead.

`.arc42` is the only knowledge folder that carries a `_c4/`, and a test enforces
that. C4's vocabulary is people, systems, containers, components and deployment
nodes; `.domain` chapters are aggregate models, and Structurizr cannot say
"aggregate root", "value object" or `0..*` any more than Archify can. `.domain`
gets a *link* to these views, not a model of its own.

## The reference is authored once, in `references.json`

```json
{
  "views": {
    "containers-backlog": [
      ".arc42/05-building-block-view.md#container-view",
      ".domain/context-map.md"
    ]
  }
}
```

That is the only statement of the link. The app reads it the other way round to
show, on a chapter, which views document it — so:

- **view → chapters** is authored;
- **chapter → views** is derived by inverting the map.

One statement, both directions, and no second copy anywhere to fall out of step.
It is also how `.domain` reaches arc42 without carrying a model: a view names a
domain chapter, and that chapter is offered the way across.

### It is a file, and the two better homes are both closed

This is worth writing down, because the obvious design does not work and looks like
it should.

**A chapter's own `related:` list.** The natural home — every other knowledge
reference is authored there, and it would put the link in the diff of the chapter it
belongs to. `.github/tools/knowledge-meta/graph.mjs` refuses it: it resolves a
reference against nodes built from `.md` files only, and `folderKindForPath` classes
anything under `.arc42/` as inside-knowledge, which makes an unresolvable target an
**error** rather than a warning. Eight chapter references produced sixteen errors and
a non-zero exit from `Update-KnowledgeIndex.ps1`. That generator is an installed copy
of the `knowledge-base` plugin's tooling and `CLAUDE.md` says never to edit it here,
so this is a constraint rather than a bug to fix. If the plugin ever learns to resolve
a `_c4/*.dsl#view` target, the app already handles a chapter-side reference —
`KnowledgeChapterLink` accepts one — and this file could move into the chapters.

**A `properties` block in the workspace or on a view.** Would keep the link with the
model, in one file, in the editor's own format. c4hero deletes it: its parser calls
`skipBraceBlock()` on `properties` at both the workspace and the view level, so the
block is parsed away and never written back. The reference would disappear the first
time somebody saved in c4hero, silently — the exact failure class this whole design
is built to avoid.

### Why `references.json` and not `index.json`

`_archify/index.json` beside a chapter is **generated**, by the renderer, and a file
with that name beside a workspace would read as generated too — something to
regenerate rather than something to review. This one is authored and diffed like the
`.dsl` is.

### What is enforced

`C4WorkspaceTests` in `tests/Backlog.UI.Components.UnitTests` pins all of it: the map
parses, every view it names exists, every chapter it names exists, every view is
documented by at least one chapter, both existing mermaid C4 fences are still in their
chapters, no folder other than `.arc42` carries a `_c4/`, and **no chapter carries a
`.dsl` reference** — because one would break the index refresh for everybody.

Each of those failures is otherwise invisible: the chapter still renders, the view
still draws, and the link between them is simply not there.

## Where it appears

The Architecture panel has two tabs, the shape the Technology panel already keeps:

- **Chapters** — the chapters, exactly as they were before this existed.
- **C4** — the explorer. Absent, not empty, when the feature is off or no workspace
  is on disk; a tab that opens onto nothing is worse than no tab.

A view was briefly listed in the chapter list instead. It did not belong there: a C4
view is not a chapter and is in no chapter, and the list is the knowledge pane's own
menu of files.

## Exploring the model

`C4Explorer` carries what c4hero calls [Explore][explore], over a mermaid render:

| Affordance | How it works here |
| --- | --- |
| Views panel | Every view, grouped by level, in the order a reader descends them. |
| Drill in | **Click a system or container in the diagram.** Each card is a `<g class="node" id="<svg id>-<alias>">`, so a click resolves by identifier and never by matching label text. Only cards with a view to drill to invite the click — the rest keep the pan cursor, because an offer is a promise. |
| Breadcrumb | Derived from the open view's own scope: *where am I*. |
| Back | Walks the history: *how did I get here*. Deliberately not the same control as the breadcrumb. |
| Search | Element names, descriptions, technologies and view titles. A hit opens the **shallowest** view that draws it — a way in rather than a destination — and rings the box. |
| Highlighter | Tag, technology, team and status. AND across facets, OR within one. Non-matching elements are dimmed, not hidden. |
| Pan and zoom | On the SVG's own `viewBox`, so zoom-to-fit is a copy of mermaid's original numbers rather than a measurement. |
| Minimap | The same SVG again at full extent, with a lens rectangle for the current `viewBox`. |
| Presentation mode | One class on the root takes every panel off screen. |
| Auto-Arrange | Not applicable — mermaid lays out on its own, and c4hero's layout sidecar is not read. |

[explore]: https://c4hero.com/features/explore

### Every gesture has a control beside it

`.design/accessibility.md` requires it, and here it is not a concession. A box in an
SVG is not a focusable target, so clicking to drill in cannot be the only way to
drill in. The same moves are the Views panel, the **Drill into** row under the
diagram, and the zoom buttons. Unplug the mouse and only the dragging is gone.

### Team and status come from `properties`

Structurizr has no field for either, so c4hero keeps them in an element's
`properties` block, and the reader reads it. Several spellings are accepted
(`owner`, `team`, `status`, `lifecycle`) because there is no standard key and asking
for one would silently find nothing. A facet with no values is absent rather than an
empty dropdown.

## What the app does with it

`.dsl` → `C4DslReader` → `C4Workspace` → `C4LayoutEngine` → `C4SvgWriter` → SVG.

**Nothing is written to disk.** The `.dsl` is the only authored source, no chapter
gains a generated block, and the repository's rule that mermaid fences are canonical
is untouched because none of this is a fence.

### Why not mermaid

It was mermaid first, and it could not be made to look like the tool the model is
authored in. Mermaid sizes its boxes from their own text, draws no icon, routes edges
its own way, and writes every colour inline where no stylesheet can reach — so a C4
view was always going to look like a mermaid diagram however it was themed. Themeing
it through `backlogMermaidTheme()` would have changed the colours and nothing else.

`C4MermaidWriter` is still here and still tested. It is the fallback, it is what the
storybook shows as "the same view as mermaid draws it", and keeping it is what makes
the swap reversible.

### The DOM contract is mermaid's, on purpose

Every card is a `g.node` whose id is `<svg id>-<alias>` — exactly what mermaid emits.
That is the only thread from a clicked shape back to a model element, and the
explorer's viewer reads it for click-to-drill, for the Highlighter's dimming and for
the search ring. Keeping the contract is why the renderer could be swapped underneath
the viewer without changing a line of it.

### Depth on one hue, not a hue per level

c4hero colours its levels with four separate hues — violet components, teal
containers, amber externals, a blue database. This product cannot copy that:
`color-scheme.md#chart-roles` says the palette carries exactly one saturated hue, and
that a second hue on one picture claims "this is a different kind of quantity". A C4
level is not a different kind of quantity, it is the same architecture seen closer.

Four steps of the one ramp was tried and read as one colour. What is drawn now is
three tiers of weight — solid for what the view is about, quieter for a person,
outline-only for anything outside the scope — with the glyph carrying what the ramp
cannot. Three tiers a reader can name at a glance, for one hue.

### `include *` does not mean every element

It means the default set for that kind of view: all people and top-level systems
for a landscape; the scope plus its direct neighbours for a context; the scope's
own containers plus the neighbours of those, with other systems left closed, for a
container view. Reading it literally is what would put a container view and a
landscape on screen as the same picture.

### Edges are rolled up

The relationships in a model are mostly between containers, and a context view
draws systems — so an endpoint the view does not draw is rolled up to the nearest
ancestor it does. Without that a context view comes out with almost no arrows,
which reads as a broken diagram rather than as a modelling choice.

Two edges that roll up onto the same pair of boxes but say different things both
survive; two that roll up identical are drawn once; one that rolls up onto itself
is dropped rather than drawn as a loop nobody modelled.

## The reader never guesses

`C4DslReader` is a **second implementation** of a dialect whose first
implementation is c4hero's TypeScript parser, in another repository, where no test
here can compare the two. `.arc42/adr/0004-knowledge-index-is-a-generated-local-database.md`
names that shape of duplication as a drift hazard — it is the same hazard as the
Archify hash rule, "the one failure mode this design cannot detect from the
inside" — and two things follow from it.

**It is specified against c4hero's own conformance fixture**
(`src/lib/dsl/__fixtures__/hierarchical-landscape.dsl`) rather than against the
Structurizr language reference, which describes a superset nobody writes here.

**Every construct outside the supported subset is reported, with its line, and
parsing continues.** Refusing the file would be the safer-looking choice and the
worse one: the failure that matters is not an unreadable workspace, it is a
readable one that draws a confident picture quietly missing whatever could not be
parsed. The panel shows the list under the view.

### Read

Workspace header; `!identifiers flat|hierarchical`; `model` with `person`,
`softwareSystem`, `container`, `component` and their nesting; `group`; positional
name / description / technology / tags; `deploymentEnvironment`, `deploymentNode`,
`infrastructureNode`, `containerInstance`, `softwareSystemInstance`; relationships
`->` with description / technology / tags, flat, dotted and relative; all six view
types with `include *`, explicit `include`/`exclude`, `autolayout`, `title`,
`description`; `styles { element … relationship … }`; comments `#`, `//`, `/* */`.

Two readings are easy to get wrong and are pinned by tests:

- **`person` and `softwareSystem` take name / description / tags; everything with a
  technology takes name / description / technology / tags.** One set of positions
  for both files a system's tags as its technology and leaves it untagged — a
  container that stops being a database and a picture that stops saying so.
- **A relative identifier resolves in its own scope first**, then each scope above
  it, then as written. Backwards, and a local name binds to a same-named element in
  another system — an edge that is drawn, and wrong.

Also worth knowing: **`#` is overloaded.** It opens a comment and it opens every
colour a `styles` block states, so the lexer treats a hash as a comment unless what
follows is exactly a hex colour. Without that, `background #438dd5` loses its value
and the style silently becomes a style with no colour in it.

### Reported, not guessed

`!docs`, `!adrs`, `!include`, `!script`, `!plugin`, `!constant`,
`!impliedRelationships`, `!ref`, `!extend`, `themes`, filtered / image / custom
views, `perspectives`, and any `include` given as an expression
(`element.tag==Database`).

### Understood and deliberately not acted on

`configuration`, `properties`, `animation`, `branding`, `terminology`, `url`.
None of them changes a picture, and reporting them would bury the constructs that
matter under noise nobody can act on.

## What this cannot say

The counterpart to Archify's "What Archify cannot say". Each of these is a place
where a faithful workspace still produces a picture that differs from what the DSL
means:

- **It is not a copy of c4hero.** The structure matches — compact cards with a
  glyph, a dashed frame with its label, curved edges with a technology under the
  description, external elements ghosted. The colour does not: c4hero spends four
  hues and this palette allows one, so levels are told apart by weight and glyph
  instead. Changing that is a decision about `color-scheme.md`, not a tweak here.
- **Layout is layered; routing is a fallback.** Cells are ranked by edge direction
  and gridded inside their frame, which suits a C4 view — actors above, the subject
  in the middle, dependencies below. Placement alone does not stop an edge crossing
  a card, so each edge is checked against every card it does not touch and rerouted
  if it hits one: first as a curve — over the row, under it, or through the gap
  between two cards — and, where no curve misses everything, as a path along the
  corridors between the cards, with corners rather than a bend. Component views need
  the second kind, because an edge across a grid has to pass a row, then a column,
  then another row, and a single curve does not have that many bends in it.

  What this is not is a general graph layout. Rank assignment is unchanged, so a
  dense view is still dense — the container view puts seven external systems in one
  rank — and routing only promises that no line is drawn *through* a card, not that
  the result is the arrangement a person would have chosen.
- **A relationship whose endpoint is a boundary is not drawn.** On a component view
  the container is the frame, so `ME -> Desktop App` has nowhere to land and is
  dropped. That is the faithful answer: the relationship is about the container, the
  model does not say which component receives it, and it is drawn on the container
  view where the container is a card. The rule was forced by mermaid, which refused
  the *whole* diagram over one such line, and it is kept because it is right.

- **Groups are not drawn.** `group` is parsed and carried, and mermaid C4 has no
  grouping construct to draw it with.
- **An infrastructure node is drawn as a card like any other**, with its glyph and
  its technology carrying what the box actually is.
- **Relationship styles are not drawn.** They are parsed — so the syntax does not
  land in the problem report — but mermaid C4 has no per-relationship styling to map
  them onto. Element `background` and `color` *are* translated, as
  `UpdateElementStyle`.
- **Shapes are not translated.** Mermaid picks a shape from the macro, so a cylinder
  is `ContainerDb` rather than a property, and a Structurizr `shape` is ignored.
- **`autolayout` direction is not honoured.** It is parsed and carried; mermaid C4
  lays out on its own.
- **c4hero's layout sidecar is not read**, so a hand-arranged canvas in c4hero does
  not survive into the app. Element declaration order is the closest thing to an
  intended arrangement the app has.

## Authoring

There is no CLI. c4hero is a browser editor and nothing in this repository runs it
or vendors it — it is not a runtime dependency, and there is no `node_modules` to
install.

1. Open [app.c4hero.com][c4hero-app] in a Chromium browser, or run c4hero locally
   from a clone (`npm install && npm run dev`; Node 22+).
2. Open the `.arc42/_c4/` folder through **folder collections** — the File System
   Access API writes saves straight back to disk. Firefox and Safari support
   single-file mode only.
3. Edit, and save. c4hero writes `backlog.dsl` and its `backlog.c4hero.json`
   sidecar.
4. Give every view a key you are happy to see in a reference, and add it to
   `references.json` against the chapters it documents. A view nothing documents
   fails `C4WorkspaceTests`. c4hero does not know about that file and will not touch
   it.
5. Run the tests. `The_committed_workspace_parses_with_no_problems` is the one that
   matters: it is what notices if a c4hero release starts emitting something this
   reader does not know.

[c4hero-app]: https://app.c4hero.com

The storybook page at `/diagrams/c4` renders a small workspace through the same
reader and writer, including the problem report, and is the quickest way to see
what a construct becomes without starting the app.
